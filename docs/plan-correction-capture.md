> 來源：卡 1／卡 2 Mac 實機驗收（同日）。使用者原話：「在終端機和 chatgpt 的輸入匡偵測不到這應該要處理」。

## 要解決什麼
SayIt 貼上文字後，使用者改了錯字，App 會讀回輸入框、比對差異，讓 AI 判斷要不要學成詞庫。實機驗收發現：在**備忘錄**能學，在**終端機**與**ChatGPT** 學不到。這兩處正是使用者最常改字的地方。

## 現況（已查證）

| App | 讀回什麼 | 原因 |
|---|---|---|
| 備忘錄 | 改後的那一句 ✅ | 原生文字框，游標位置準 |
| 終端機（cmux／Claude Code） | 畫面上別行的文字 | 讀取時只取「游標前後各 50 字」；終端機的全文是整個捲動紀錄、游標位置不準 → 取到別行（實機兩次皆如此） |
| Chrome 裡的網頁（ChatGPT 若是網頁版） | 空 | 探針實測：Chrome 預設只回報整頁 `AXWebArea`、長度 0，不暴露頁內輸入框；SayIt 的「讀改後文字」路徑沒有像「讀選取」路徑那樣先喚醒 AX 樹 |

## 退步守衛（R3 裁決：恢復）
- v0.16 在送 AI 前有「讀到的文字和貼上原文重疊 < 30% 視為讀錯、跳過」；卡 1 換新比對時拿掉了 → 終端機讀到別行時，不相干的畫面內容可能送給第三方 AI（安全審查 MEDIUM）。生產者：終端機讀回別行（實機兩次）。
- **R1 定序**：本機選出區段 → 非空 → 區段重疊率（分母＝選中區段的 Unicode 字元數，不用整個畫面）< 30% 跳過 → `hasInternalCorrection` → AI。AI、日誌、配對函式**一律只用同一個選中區段**。
- **已知取捨（R1 MED，照寫不暗降門檻）**：大幅改寫（例：「扣伯涅提斯」→「Kubernetes」，重疊約 20%）會被守衛擋下、學不到；寫進說明。
- **R3 生產者實證**：A 欄位貼上 → 滑鼠換到 B 欄位打字停手 → 游標有效但讀到 B 的無關內容；拿掉守衛時 AI 被呼叫 1 次（應為 0）。守衛同時適用游標摘錄與 B1 錨點回傳值。

## 做法（三方定案法仲裁版，取代 R1／R2 的相似度搜尋）

> 依據：自我檢討版 `$CLAUDE_JOB_DIR/tmp/rederive-terminal-step1-self.md`、codex 獨立版（推薦終端機不學；其「每次只讀一次畫面」錨點為派工端任務單錯寫，仲裁已排除）、Fable 仲裁（2026-11-28）。上層判斷：是「設計得太複雜」，不是「不該做」。

### B0. 守衛（無論如何先落，約 3 行＋測試）
- 游標回報 0 時，不回傳游標摘錄。關掉獨立版重現的兩條 HIGH（畫面最上方歷史進日誌與 AI、舊人名成配對）。
- 30% 重疊守衛：**恢復**（R3 裁決，見上方退步守衛段；仲裁「不恢復」的主張作廢）。
- **已知漏學**：一般 App 裡使用者改完把游標移到文首（游標真的是 0）再停手 → 這次不學。接受（漏學可手動加詞），寫進說明；先前「備忘錄不受影響」的說法作廢。

### B1. 終端機等值錨點（P1–P4 實測通過才做）
1. **基準**（R6 改：以貼上前後的文字變化證明本次插入區段，取代「全文含原文、取最後一次」）：Rust 在模擬貼上**之前**記下聚焦 AX 元素參照與其全文 S前（以本次辨識識別碼為鍵，只留在 Rust 記憶體）。貼上後的讀取中，若游標為 0、尚無基準、該次元素 `CFEqual` 貼上前元素 → 以 S前 與本次全文 S0 去掉最長共同前綴與共同後綴，中間差異區段必須**逐字等於**貼上原文；且共同前綴長＋共同後綴長 ≤ S前 長（否則插入位置可左右平移、有歧義）→ 才以此區段建立基準。差異不等於原文（含：貼到別處所以 S前＝S0、畫面其他地方同時重繪、貼上尚未出現）→ 本輪輪詢繼續嘗試，直到停手仍無基準即跳過。基準記下：貼上段所在行、其上方全部行、緊接下一行（R4 曾列可刪；R5 找到生產者：尾端裝飾為空時多折一行會被截成半句 → 保留）、同行前後裝飾字（提示字元、框線）。
2. **只在停手時核對**（閒置／硬上限的最後一次讀取；輪詢期間回空）：聚焦元素與貼上當刻元素相同（R4／R5：防另一分頁；pid 比對 R5 列可刪、已拿掉）、上方所有行逐字相同、緊接下一行逐字相同、貼上段自身的行數不變（不檢查全畫面總行數）、前後裝飾不變 → 回傳去掉裝飾的中間文字＝「貼上那段現在變成什麼」，再交既有內部改正判定 → AI → 配對。
3. **跳過**：監看期間按過**白名單以外**的任何鍵 → 本輪取消（R8 改黑名單為白名單：Esc <、PageUp、vi 模式 Esc k 等叫出歷史的方式列不完）。白名單＝不帶 Ctrl／Option／⌘ 的可列印字元鍵（Shift 可）、空白、Backspace、Forward Delete、左方向鍵、Enter（照既有選字防抖）；右方向鍵不在白名單（R9：zsh 自動建議以右鍵接受整句歷史）。由既有鍵盤監看 event tap 設旗標、隨本輪結果回報。已知漏學：右鍵移游標、Option＋方向鍵跳詞、Tab 補完等進階編輯，該輪不學；沒有基準（含使用者在第一次輪詢前就改完、基準沒建立）、任一錨點不等、Enter 結束 → 回空，不重試不猜。Enter 結束一律不確認、不學（契約，不是暫缺）。多行貼上的範圍＝貼上原文首字所在行到末字所在行。
4. **隱私**：整個畫面只留在 Rust 記憶體；跨出 Rust 的只有「貼上那段位置上現在的文字」。基準以本次辨識識別碼為鍵。
5. 規模：Rust 約 80–110 行＋測試約 80 行；前端約 10–15 行（多傳原文、識別碼、是否最後一次讀取）。

| 反例 | 行為 |
|---|---|
| (a) 上方舊原句、底部改成「陳泰呈」 | 貼上前後差異＝底部新插入段；上方沒變 → 回傳「請找陳泰呈確認」 |
| (b) 上方歷史「陳泰文」 | 歷史不是貼上位置，永遠不回傳 |
| (c)「陶里」→「Tauri」變長 | 無長度限制，完整回傳；多折一行則跳過 |
| (d) 三行只改中間一詞 | 三行整段回傳，既有配對函式處理 |
| (e) 改完後捲動／新輸出 | 上方不等 → 跳過 |
| (f) 改完立刻 Enter | 跳過（白話：在終端機改完要停約 3 秒才會學） |

### 被砍掉（寫進決策紀錄，避免重提）
R1 固定視窗取最高分；R2 游標摘錄優先、最後 40 行由下往上、合併相鄰行；自我檢討版的「× 3」尺寸門檻、「只有一段」條件、「擴到行邊界」（會外送提示列）；獨立版的宿主名冊、「使用者明確指定配對」介面；Enter 路徑在終端機的快照退回；送出後回顯確認（待 P6）。
- 獨立版兩條重現測試（`/private/tmp/codex-review.aChZs3/capture-review.test.cjs`）實作時轉成 repo 內回歸測試。

### B2. 終端機結果只進收件匣（2026-11-28 使用者拍板 A）
- 根因：shell 能用白名單內的鍵（`!!`＋空白鍵等）把輸入列換成任意歷史句，SayIt 從外部無法證明「這句是使用者親手改的」；鍵盤監看看不到注音輸入法送出的字，也無法佐證。
- 做法：B1 路徑產生的新詞與錯字配對，一律以「待確認」進收件匣，**不直接寫入詞庫、不直接生效**；使用者按「套用」才生效，忽略即不影響。一般 App（游標有效）的路徑不變。
- 猜錯的後果因此從「詞庫被汙染」降為「多一則可忽略的建議」，R10 的 `!!`＋空白鍵案改列已知殘餘、不擋卡。
- 隱私邊界不變：30% 守衛、只送讀回區段給 AI。

### C. ChatGPT 桌面 App：讀不到才喚醒
- 先讀；只有 Rust 解析不到聚焦文字元素（AX 回報無聚焦元素或元素無文字屬性）這個原因分支才對該 App 設（R6 M2：B0 拒絕、B1 輪詢期間回空、空欄位都不觸發）， `AXManualAccessibility` 與 `AXEnhancedUserInterface`（與「讀選取」路徑共用設定函式），**不新增等待迴圈**：靠既有的監看輪詢與結束時重讀；不保證下一次必讀到（探針只證明數秒後可讀），讀不到該次就跳過。讀得到的 App 不設任何屬性。
- 冷啟動、快速 Enter 時第一次可能還讀不到 → 該次跳過，屬可接受（已記錄）。測試補「第一次讀 None、喚醒後第二次讀到」的延遲就緒案。

### 不做
- 不模擬 ⌘A／⌘C 去剪貼簿讀（v0.9.1 #24／#25）。
- 不做每個 App 的專屬規則表；不處理 Chrome 網頁。
- Windows 本卡不動。

## 驗收
1. 守衛測試：讀回與原文無關（含 R3 換欄位情境）→ 不呼叫 AI；相關且有改 → 照常分析；大幅改寫被擋（已知取捨、斷言被擋）。
2. 隱私測試：選中區段周邊放哨兵文字，斷言送 AI 的參數與日誌都不含哨兵。
3. Rust 等值錨點單元測試：反例 (a)–(f) 逐案；B0 守衛（游標 0 不回摘錄）；獨立版兩條 HIGH 轉回歸測試。
4. 喚醒只在讀不到時觸發；與「讀選取」共用設定函式，既有選取測試不回歸。
4. 實機（測試身分 `com.sayit.app.hwtest`）：終端機、ChatGPT、備忘錄各改一個專有名詞，三處都進收件匣；做不到的列為已知限制並在說明裡寫清楚。

## Chrome 實機結果（2026-11-28，使用者在場）
- 探針（直接鎖定 Chrome、對 App＋每個視窗設 `AXEnhancedUserInterface`）：冷啟動喚醒前讀不到、喚醒後約 4 秒讀到網頁輸入框文字。
- SayIt 實測第一輪失敗：系統層 `AXFocusedApplication` 在冷啟動 Chrome 回空，程式在喚醒前就返回；且只設 App 不足（Chromium 以主視窗上的屬性判斷）。
- 修法（卡 5 C 段擴充）：解析聚焦 App 時，系統層回空就退回 NSWorkspace 前景 App；讀不到聚焦文字時，除 App 外也對每個視窗設同組屬性。
- 修後實測：冷啟動第 1 次讀空（預期）、第 2 次讀到但重疊 29% 被守衛擋、第 3 次學到「沈伯洋」→ **Chrome 網頁輸入框可參與改字學習**；已知限制：Chrome 啟動後第一次改字學不到。
